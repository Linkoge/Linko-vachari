# Linko MyMarketer

An installable, private PWA for preparing and explicitly publishing MyMarket listings. Add photos, title, price and description on one page; choose an account and category, then queue publication with one click. Four sections: **New listing**, **Drafts**, **My listings**, and **Settings**. React editor, Express server, SQLite submission journal, semantic Playwright automation and locally signed-in Codex CLI or Claude Code CLI decisions.

## Run locally

Requires Node 22.13+, pnpm 10, Chromium dependencies, and Xvfb on a Linux server for the private headed browser. The operator signs in to Codex CLI with ChatGPT or Claude Code CLI with a Claude subscription under the application's OS account, according to each saved AI slot. No API key is required or accepted by the panel.

```sh
corepack pnpm install --frozen-lockfile
corepack pnpm browser:install
cp .env.example .env
codex login status
# Only if needed, use Codex's supported interactive sign-in:
codex login
# Or use codex login --device-auth where enabled by your account.
corepack pnpm build
corepack pnpm start
```

Open `http://127.0.0.1:4310`. The default is a trusted local workspace. `pnpm dev` runs the editor with Vite instead of the production shell. Keep the server running for uploads, category discovery and listing work. Do not bind it to a public interface.

Codex uses its own saved ChatGPT sign-in through supported [non-interactive execution](https://learn.chatgpt.com/docs/non-interactive-mode) and [authentication](https://learn.chatgpt.com/docs/auth). Account/model availability and usage limits still apply. This application does not read, export or duplicate Codex authentication tokens. It supplies item text and redacted live page observations through stdin, requests schema-constrained decisions, disables tools and extra agents, and validates the result. Category selection supplies the chosen cover photo; credentials are never supplied. Native sign-in and one real structured Codex decision were verified on this host; full authenticated marketplace integration remains unverified.

The previously prepared artifact predates this opt-out change and must be rebuilt to include it.

2. Open **Settings → MyMarket accounts** and add a label, email and password. Each account has a separate persistent browser profile. Select the account on the draft; new drafts default to the last account you selected or added.
3. Listing automation signs in automatically using that account's stored details whenever needed, including a sign-in form encountered mid-run. If MyMarket asks for an SMS/email code, a **MyMarket verification** prompt opens. Enter the code there; it is masked, held in memory, and cleared after sending. Challenges the assistant cannot complete stop the task with an error; retry when resolved.

Account details are stored server-side in `LINKO_DATA_DIR/mymarket-accounts.json` (0600, ignored by Git), never returned by APIs, sent to AI, or included in drafts or browser bundles. The existing `mymarket-account.json` credential (or initial environment seed) and `browser/` profile become the first account, `legacy`, without moving or losing the existing profile. Migration attaches older drafts and listing recipes to that account and preserves existing submission claims. New profiles live in `browsers/<account-id>/`. Account IDs are immutable and browser jobs are serialized; monitoring, deletion and re-listing always select the saved listing's account. Never run a separate browser script against a running service's profile.

Settings and the draft account picker show **N of 5 free listings used** for tracked active listings in each account. Paused monitoring and inconclusive checks retain their count; a witnessed missing, replaced or owner-deleted listing frees its slot. Listings created outside this app are not imported or counted. This is a usage indicator, not permission to purchase additional listings; paid controls remain blocked. Removing an account deletes its saved credentials and disables automation for its references. Its history and browser profile are retained for recovery and never reassigned. Changing the login identity requires a new account; the credential form cannot attach a different identity to an existing profile. An environment seed is not restored after removal; remove any obsolete seed from your private runtime environment too. If all accounts are removed, add an account before creating or preparing listings.

## Listing workflow

1. Upload one to eight JPEG, PNG or WebP photos (12 MB and 40 megapixels each). Choose the cover by tapping its photo; arrow buttons reorder the gallery. Photos are normalized to EXIF-free JPEGs and saved immediately. The chosen cover is uploaded first, followed by the remaining photos in the saved order.
2. Enter title, price and description and choose the listing account. Every text, account, category, fact, cover and order change autosaves after 500 ms; uploads/removals persist immediately. **Drafts** lets the owner resume or delete a draft from any device. Each tab has an independent active draft, with per-draft offline storage. Optimistic revisions reject stale writes to the same draft (including photo uploads/removals) without overwriting another device's edits. Reload the saved draft to resolve a conflict. Editing other drafts continues while browser jobs run.
3. **Find category** uses the stored full category tree in `LINKO_DATA_DIR/category-tree.json`. Missing, root-only or older-than-seven-day trees refresh automatically. Operators can also refresh through the existing private API or category script; the main UI has no category maintenance panel. The crawler reconstructs all ancestors from the live category ID/parent graph, or traverses witnessed category links, without AI or publishing calls. It replaces the tree atomically after traversal and rejects root-only results, retaining the previous file. Everyday AI infers the object class from the title/model, description and cover (for example Canon EOS 600D can be classified without writing “camera”). Small trees supply every leaf path (up to 160 leaves and 24 KB); larger trees navigate direct children level by level, retaining at most three uncertain branches. No literal-word pre-filter drops categories. Final choices and up to three inline candidates must be exact leaf paths; parents, including implicit ancestors, are rejected. Choose a candidate or edit the category path directly. Missing/unusable trees, no fit, or a category withdrawn from the live form use the retained comparable-search fallback (three or four searches and witnessed detail-page breadcrumbs). Known parents are excluded there too; uncertain witnessed leaves appear inline. Preparation and final audits require a leaf accepted by the live form. The selection method (`tree`, `comparable-search`, or `owner`) stays in the recipe.
4. **Publish** saves outstanding edits and returns HTTP 202 with a durable job and a fresh empty draft immediately. It requires **Settings → Publish**, which remains off by default on new installations. A disabled Publish button shows one short inline reason, linked to Settings when publishing is off; missing photos, title, description, positive price, account, offline state and locked drafts have their own reasons. No intermediate review or confirmation screen appears: the Publish click authorizes that job's single guarded submission. The server finds the category if needed, fills the live form, derives required attributes only from supplied text with exact evidence, and performs the existing final audits. Unknown required facts appear inline when the owner opens that job's draft; answer and press Publish to continue. Uncertain categories also return to the same page for a choice. Optional controls retain their defaults. No item specifications are invented.

Jobs persist in SQLite and continue with the panel closed. **My listings** combines jobs and published history without duplicate rows on retry. Each row shows the cover, title, price/currency, account label, status (`queued`, `publishing`, `live`, `Needs info`, `failed`, `deleted-by-me`, or `relisted`), a MyMarket link when a public URL exists, and Delete. Queued jobs have no public link until publication is verified. Jobs awaiting required fields show **Needs info**, a short reason and an **Open draft** link. Answer the questions directly above Publish (a select is used when the form supplies options), then press **Publish** to resume. Account-level city/phone answers offer **Save as account default**. Existing needs-input drafts use this same flow after an update. Real failures and inconclusive/missing marketplace checks show `failed` with a short reason; drafts without a submission attempt can be reopened. Unknown attempts stay locked and appear as `failed`; inspect MyMarket directly. Published listings have no in-app editing, draft links, downloads or monitoring controls. Removed accounts retain their labels in history. Failures and missing facts send best-effort Telegram notifications using the saved connection. A single browser FIFO serializes all jobs, including jobs for the same account; different tabs/devices can queue independently and keep editing. Untouched queued jobs resume after restart. Interrupted running jobs require owner attention; an interrupted final submission remains unknown and locked, never automatically retried. Removing an account causes its queued jobs to fail safely. Existing monitoring shares the same browser lock.

Automation uses current DOM labels, roles, values, options and transient element handles. AI cannot choose arbitrary selectors, coordinate clicks, credentials, payments or the final publish action. Bounded retries re-observe the page; final publication is never automatically retried. The queued snapshot is locked against edits; its revision, browser session, field/photo hash and final semantic audit must pass.

A durable SQLite claim prevents repeat publication of identical content/photos across draft IDs within an account. A success receipt requires an observed confirmation and a public listing page with matching title and price. An uncertain outcome becomes **unknown**, including a process interruption; inspect the account manually before any further action. Uncertain attempts are never automatically unlocked or retried.

### Saved records and deleted-listing recovery

Before every final submission, the app saves a private Markdown recipe to `LINKO_DATA_DIR/listings/<draft-id>.md` (default `.private/listings/`). It includes the complete category/section path, exact title and description, price/currency, supplied facts, observed non-private form fields (including optional/default controls), and photo filenames in cover-first upload order. A verified receipt and subsequent monitoring results update that file. SQLite retains the immutable recipe and replacement chain. Keep the **entire private data directory**, including `workspace.sqlite` and `photos/`, in backups: the Markdown alone does not contain the image bytes. Credentials, cookies and account/contact form controls are excluded. Older successful listings are backfilled from their saved draft/review when the server starts; their records can only include fields the older version retained.

The server checks verified listings every **three hours**, including overdue checks after restart. It waits for listing work and an unexpired form review to finish. Monitoring and re-listing run in the background; **My listings** shows compact listing status without diagnostic messages or per-item monitoring controls. Markdown recipes are still available at `/api/listings/<id>/record` for operators. Records remain available through the private API with the same access and no-cache rules as drafts. Monitoring continues while the server runs, even with the panel closed.

Automatic replacement requires **Settings → Publish** and **Auto-relist** to be enabled. They are saved atomically in `LINKO_DATA_DIR/settings.json`; when automation settings are absent, `ALLOW_PUBLISH` and `LINKO_AUTO_RELIST` supply their initial values (both default false). Saved values take precedence on restart. Both controls save immediately; disabling publishing prevents queued jobs from submitting, and disabling auto-relist stops automatic replacements while monitoring continues.

**Retire ads through My listings → Delete → Confirm deletion.** For a published ad, the app uses the existing signed-in MyMarket deletion flow and stores a durable `deleteRequestedAt` marker before any browser action. A verified deletion displays `deleted-by-me` (`deleted_by_owner` internally) and permanently stops re-listing. An interrupted or uncertain deletion displays `failed`, retains the permanent marker and cannot be blindly retried. Inspect MyMarket directly if needed. A job still queued can be cancelled by the same Delete action without opening MyMarket; its job and deletion marker persist together and it can never publish after restart. Delete is disabled while publishing/re-listing and on retired records. The old row of a verified replacement displays `relisted`; the new listing has its own row and Delete action. Deleting directly on MyMarket bypasses the owner marker, so a public 404 would look like a marketplace deletion.

Recovery requires two HTTP **404/410** responses for the exact saved public URL, separated by at least **one hour** (first missing response → confirmation one hour later). Regular checks remain every three hours. Before counting any 404/410, an independent browser tab must load the MyMarket home control successfully (HTTP 200, recognizable content, no challenge, login or error shell). A failed control means **unavailable**, resets missing evidence and never triggers re-listing. All checks are script-only and make no AI calls. Timeouts, redirects, login pages, browser challenges, server errors, changed content and ambiguous 200 responses reset the evidence and never trigger publication. Some MyMarket removals may use a 200 error shell; those are reported as inconclusive until their actual behavior can be verified. The monitor replays learned semantic browser steps for the exact saved category path, fields, text, price and cover-first photo order. Field states, required fields, form text (including category/fee notices), photo order, duplicate claims and the final control are audited deterministically, and the old URL plus its control are rechecked immediately before the one guarded submit. An unchanged recipe uses no AI, including receipt verification. If a control or form changed (or an older recipe has no learned steps), **Fix-it** repairs that run with the same saved recipe. Successful preparation saves updated semantic control signatures and steps in the private recipe; receipt confirmation text is learned after a verified submission. Delete uses the same script-first approach and saves successful learned delete controls in SQLite. AI never submits or repeats a final publish/delete click; it only proposes semantic targets or interprets an already-submitted receipt. Unknown facts, uncertain model responses, provider errors and uncertain clicks stop with **attention**. No blind publish retry follows. Existing field, fee, photo and publication audits still apply. It preserves the saved recipe; if a category is withdrawn, preparation can use comparable search to recover a current path without inventing fields. The replacement gets its own record and future checks; the old record is retired.

Unknown new form requirements, uncertain Fix-it decisions, sign-in issues, missing photos, interrupted preparation and uncertain submissions stop automatic recovery for that item and show **attention**. Inspect the MyMarket account. A blocked draft that has not reached a submission attempt can be resumed from Drafts and queued again with Publish; an unknown publishing attempt remains locked. Neither restarting the server nor resuming monitoring retries such an attempt. Fixture tests cover confirmed deletion through a verified replacement; no live listing was published or removed for this feature.

## Settings: AI and Telegram

**My listings** is always available from navigation, with an empty history message before the first queued or published listing.

**Settings → Accounts** stores a default city and listing phone separately for each account in the private server data directory (`mymarket-accounts.json`, mode 0600, ignored by Git). Existing and new accounts start with **თბილისი (Tbilisi)** as the saved default city, without a district or area. Every new listing prefills a small editable City field; changing it affects that listing only. Choosing another account uses its saved city. Enter each account’s phone once here; publishing fills the required mobile field automatically, or accepts the phone already filled by MyMarket’s profile. Old drafts with an empty city use their account default when resumed. Phone values stay out of AI prompts, learned form recipes and the offline draft cache.

Open **Settings** from the four-section navigation on desktop or mobile. It contains only MyMarket accounts, the AI picker, Telegram, and Publish/Auto-relist toggles. Setup prose, provider readiness, category refresh and diagnostic panels are absent. Panel sign-out remains in the header on protected remote workspaces. The **AI** section has exactly two slots:

- **Everyday**: category choice and field matching for new listings. Default: Codex CLI, `gpt-6-luna`, low reasoning.
- **Fix-it**: only after a saved script fails because the page changed. Default: Codex CLI, `gpt-6.1-sol`, high reasoning.

Each slot saves its provider (Codex CLI or Claude Code CLI), exact model name and low/medium/high effort. The picker follows the host's Linko Bot Manager: three-column model buttons with a thinking/effort row underneath each provider. Choose a model to select its provider; only that provider's effort row is enabled. Model buttons highlight the saved choice; the selected effort uses accent text. Arrow keys and Home/End move focus within a row; Enter/Space selects. The compact layout works on desktop and narrow phones.

Every model or effort selection saves immediately. The highlight changes only after the server confirms the saved pair; both slots are disabled while saving. Failed or lost responses reload the saved settings. If that refresh also fails, choices are hidden until **Retry settings** or reconnection succeeds. Offline controls are disabled. Closing/reopening or reloading shows the same saved choices used by jobs; there is no separate AI Apply step or unsaved selected model.

Codex model buttons and supported efforts come from the installed CLI's `app-server` `model/list` response (cached for one minute), with Luna/Sol/Astra first when listed. Hidden models and unsupported efforts are excluded. If discovery fails, Codex choices stay empty; no guessed IDs are offered. When installed, Claude offers the verified CLI aliases `haiku`, `sonnet`, and `opus`. The API rejects changes to unlisted model/effort pairs. Other saved IDs remain readable but are shown as unavailable rather than selectable when absent from the catalog. The two obsolete bundled Codex defaults (`gpt-5.4-mini`, `gpt-5.4`) are migrated on read to Luna/Sol without rewriting the settings file; other saved choices and providers are preserved.

Settings live atomically in `LINKO_DATA_DIR/settings.json` (0600), not environment variables. `LINKO_CODEX_MODEL` is no longer used. CLI executable paths (`LINKO_CODEX_BINARY`, `LINKO_CLAUDE_BINARY`) and the bounded decision timeout (`LINKO_CODEX_TIMEOUT_MS`, default 180 seconds) remain operator runtime options. Missing CLI, missing local subscription sign-in, inaccessible model or unsupported effort fails clearly, never switching providers. CLI sign-in readiness remains available through the private API; model access is verified by the actual decision. If needed, the operator runs `codex login` or `claude auth login` outside the app. No provider API keys are accepted or passed to either CLI.

Codex uses [schema-constrained non-interactive execution](https://learn.chatgpt.com/docs/developer-commands?surface=cli). Claude uses [print mode, JSON schema, explicit model/effort and disabled tools](https://code.claude.com/docs/en/cli-reference), with no session persistence, no project/user setting sources, disabled hooks and no MCP servers. Keep both CLIs current enough to support these flags; unsupported versions fail rather than changing providers. Both transports redact input, keep bounded CLI error streams only in memory, validate JSON and kill the process group at the timeout. Decision errors identify usage limits (including reset time when supplied), unavailable model/effort, timeout, invalid schema, non-JSON output, image problems or CLI execution failure, with at most 200 characters of redacted CLI detail. Prompt transcripts, raw JSON parse errors and Zod values are never shown. All 13 decision schemas live in `server/decision-schemas.ts`: wire schemas use required properties, closed objects and a conservative keyword subset, while Zod still enforces application bounds after parsing. Cover attachments use their detected JPEG/PNG/WebP extension and MIME type. Claude image calls use matching stream-json input/output and parse the final result event. Category lists contain at most 160 paths and 24 KB of UTF-8 JSON; no-overlap sampling spans category roots and uncertain selections retain the comparable-search fallback. The shared decision timeout defaults to 180 seconds and can be set with `LINKO_CODEX_TIMEOUT_MS`. Account tokens are never read or copied. Only category selection attaches the chosen, EXIF-free cover photo; other decisions use text observations.

In **Telegram**, create a bot through **@BotFather** (`/newbot`), paste its bot token, and save. Open that bot and press **Start**, then send it a message. Use **Detect chat ID** to read private-chat IDs from `getUpdates`; choose yours and save again. **Send test message** verifies the saved connection. If Telegram returns no chat, message the bot again; a bot already using a webhook may need a separate bot for this app. **Disconnect Telegram** removes the saved settings.

The bot token is write-only in the UI, registered for redaction, never included in API responses or logs, and stored only in the private settings file outside Git. Notifications cover confirmed marketplace deletion, successful re-listing with its new URL, script failure/Fix-it start, successful AI repair, and attention. Delivery is best effort with four-second timeouts, bounded response size/concurrency and no automatic delivery retries; notification errors never block monitoring. Test/detection buttons report delivery/setup failures without exposing raw Telegram responses. Keep settings, SQLite, photos and browser state together in private backups.

## Privacy, offline use and limitations

Secrets, cookies and drafts remain in the ignored server data directory (default `.private/`, mode 0700; file creation mode 0600). MyMarket credentials live in `.private/mymarket-accounts.json` (the original `.private/mymarket-account.json` is retained during migration), panel password/allowlist hashes in `.private/access.json`, and browser cookies/sessions in `.private/browser/` and `.private/browsers/<account-id>/`. If `LINKO_DATA_DIR` is set, these paths are relative to that directory; keep it private and outside tracked assets.

For local environment credentials, copy the empty placeholders from `.env.example` into the ignored `.env` in the workspace root and restrict it with `chmod 600 .env`. The server loads this file through `dotenv`; exported environment variables take precedence. `MYMARKET_PHONE`/`MYMARKET_PASSWORD` are an optional server-only seed on the first account migration; Settings is the normal way to add accounts. Keep existing private files locally when updating the checkout. Never put credentials in examples, evidence, screenshots or source code. Codex and Claude Code keep their own sign-ins outside this repository; the application does not copy them.

`pnpm test` includes a permanent index check that rejects tracked environment files, private keys, credential JSON and cookie/token/session data, even if force-added or missing from the working tree. Only `.env.example` and `runtime.env.example` are allowed environment templates, with empty credential fields. `pnpm security:check` also scans reachable git history without printing credential values. If a real credential is found, retain its local copy, remove it from the index with `git rm --cached -- <file>`, and rotate it with the service provider. Removing it at HEAD leaves historical exposure intact; do not rewrite history or force-push as part of this cleanup.

Runtime files are not encrypted at rest. Use a trusted OS account and encrypted disk. This is one owner's workspace and several isolated marketplace accounts; authorized panel users share it. Loopback is a trusted OS boundary: unrelated local processes must also be trusted. Remote access requires the exact configured HTTPS origin, trusted loopback Tailscale proxy, allowlisted identity and CSRF checks. A secure panel session is also required unless `LINKO_PANEL_AUTH=false` explicitly disables the panel password; passwordless users share the trusted workspace. Tagged devices without user identity fail closed.

The PWA caches the public shell and saves draft text/previews in IndexedDB. Private API responses and credentials are not cached by the service worker. Offline text edits autosave to the server after reconnecting unless a newer server revision conflicts; uploads and publishing are never queued offline. Panel sign-out clears local draft storage. Anyone using the same unlocked browser/device can access its offline drafts; keep the device private.

Cloudflare: the earlier 403 came from automation fingerprints (the default `HeadlessChrome` user agent, like curl's default agent). A headed, persistent real-Chromium profile on the private Xvfb display with the automation flags removed is admitted (HTTP 200); headless is only admitted with a normal user agent. The browser layer also waits out interstitials and dismisses MyMarket's cookie/promo overlays. See the [execution report](docs/EXECUTION_REPORT.md#agent-driven-sign-in-and-cloudflare-findings) for exactly what was verified live. MyMarket signs in on `auth.tnet.ge` (email or phone + password, invisible reCAPTCHA). **Verified live with the owner's real account (2026-10-15):** email + password sign-in succeeded with no SMS/email code, the session persisted in the browser profile and was reused on the next run, and a sample listing was prepared up to the pre-publish review (category found from live comparables, full category path selected, condition/price/title/description/required dropdowns filled from the draft, three photos uploaded cover first and verified in order) without clicking publish. Sign-in passes through single-sign-on hops on sibling auth hosts (`auth.myauto.ge/?AccessToken=…`), which are allow-listed; the live form uses react-select dropdowns, `fast-option` rows, hidden button-styled radios (selected state is an `active` class) and an uploader that shows a multi-file selection out of order, so photos are uploaded one at a time and the gallery order is checked. A real submission receipt remains unverified; the app must still discover new required attributes during use and fail closed. Video upload support could not be established from public material or an authenticated uploader; stage one is photo-only, with video an optional later extension.

## Automated deploy

The root `.linko-deploy.json` registers the four executable scripts in `deploy/` with the manager. After merge, its serialized deploy queue runs backup, deploy and mandatory health checking; a failed deployment or health check uses rollback. Scripts take no arguments and support environment overrides. By default they archive the repository containing the scripts at `HEAD` and share a private backup at `~/.local/share/linko-mymarketer/backups/pre-deploy`, so the saved commands require no injected deployment variables. The service runs from `~/.local/share/linko-mymarketer/releases/current/app`, where `releases/current` is a symlink switched atomically to `releases/<UTC timestamp>-<commit12>/`. Runtime configuration stays in `~/.config/linko-mymarketer/runtime.env`; the scripts read only its `LINKO_DATA_DIR` path and never print it. The unit derives `LINKO_RELEASE_ID` from the real release directory, so `/api/health` reports the deployed release.

| Script | Environment | Effect |
| --- | --- | --- |
| `deploy/backup` | optional `DEPLOY_BACKUP_DIR` | Writes `record.env` (active release, from `current` or a legacy pinned unit; data path; time), copies the private data directory to `data/` and the installed unit to `unit.service`. |
| `deploy/deploy` | optional `DEPLOY_REPO`, `DEPLOY_COMMIT` | `git archive` of the commit into a new release, `pnpm install --frozen-lockfile` and `pnpm build`, installs the release's unit file, `systemctl --user daemon-reload`, atomic `current` switch, `systemctl --user restart linko-mymarketer.service`. A failed build removes the partial release and changes nothing live. Keeps the newest 5 script-built releases (`DEPLOY_KEEP_RELEASES`), never the active or previous one and never hand-prepared releases. |
| `deploy/health` | optional `DEPLOY_HEALTH_URL` (default `http://127.0.0.1:4310/api/health`) | `curl --max-time 10` retried for 60 s, plus an active user service. HTTP 200 must identify this application and the active release. Protected panels may return only the exact application login-required 401 or tailnet-identity-required 403 response. Redirects, other errors and malformed responses fail. Those access denials verify application readiness but cannot verify its release ID. |
| `deploy/rollback` | optional `DEPLOY_BACKUP_DIR` | Restores the saved unit, points `current` back at the recorded release and restarts. For a first installation with no prior unit or release, stops the new service and removes its unit/current symlink. Data is kept as is; `DEPLOY_RESTORE_DATA=1` also restores the backed-up data directory (the replaced one is kept beside it as `*.pre-rollback.<time>`). |

Other optional variables: `LINKO_DEPLOY_ROOT`, `DEPLOY_RELEASES_DIR`, `DEPLOY_UNIT_DIR`, `DEPLOY_ENV_FILE`, `DEPLOY_DATA_DIR`, `DEPLOY_SERVICE`, `DEPLOY_PACKAGE_MANAGER` (default `corepack pnpm`), `DEPLOY_STEP_TIMEOUT_SECONDS` (600 per install/build step), `DEPLOY_SYSTEMCTL_TIMEOUT_SECONDS` (60). Deploy refuses a commit whose unit file does not run from `releases/current/app`. The data copy is a plain `cp -a` of the live directory, taken before the restart. The host must already have Node 22.13+, corepack/pnpm, curl, Chromium/Xvfb and the owner’s private runtime environment; deploy fails before switching releases if that environment file is missing. It preserves runtime configuration and the existing tailnet route; it does not create public routes or host prerequisites. In-process monitoring and publishing jobs run with this single service; there are no separate scheduled-job units. `tests/deploy.test.ts` exercises the saved argv commands, failure handling and all four scripts in disposable directories with fake `systemctl`, `curl` and package-manager shims. No live deployment is performed by those tests.
